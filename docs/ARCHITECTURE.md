# Architecture (services as of platform P1; request paths as of phase 2)

This file describes what exists. The target architecture is in FLATSHARE_BACKEND_SPEC.md
sections 5 and 8; deviations are in DECISIONS.md.

## Request path

```mermaid
sequenceDiagram
  participant W as Website server / test client
  participant P as Caddy
  participant E as Endpoint workflow (wf.api.*)
  participant G as wf.gateway.auth
  participant DB as PostgreSQL
  W->>P: signed request /v1/...
  P->>E: /webhook/v1/... (raw body kept)
  E->>G: webhook item + route contract
  G->>G: Prepare: path, canonical query, raw body (Code)
  G->>DB: app.gateway_check: verify HMAC, nonce, user context, rate counters
  G->>G: Decide: 401/403/422/429 rules (Code)
  G->>DB: app.idempotency_begin (state-changing routes)
  G-->>E: ok + context, or rejection, or stored replay
  E->>DB: handler queries (e.g. upsert user)
  E->>DB: app.api_finish: ai.executions row, idempotency complete/release
  E-->>P: envelope + X-Request-Id
  P-->>W: response
```

Three or four database calls per request, all parameterised. Secrets never pass through n8n:
the HMAC is computed inside PostgreSQL by a function `n8n_worker` can call but whose key table it cannot read.

| Role | Used by | Can |
|---|---|---|

```mermaid
flowchart LR
  CSV[kb/packs/*/sources.csv] -->|scripts/kb.py seed| SRC[(kb.sources)]
  API[POST /v1/admin/kb/ingest] --> JOB[(app.jobs)] --> W[wf.kb.ingest]
  W -->|per source| S[wf.kb.ingest_source]

  S -->|bytes| RAW[(kb.raw_fetches)]
  S -->|cleaned text, new version if changed| DOC[(kb.documents)]
  S -->|/tokenize| TEI[TEI]
  S -->|A fixed_500_50, B structure_aware_v1| CH[(kb.chunks + spans + tsv)]
  S -->|/api/embed| OL[Ollama bge-m3]
  S -->|/embed passage:| TEI
  OL & TEI --> EMB[(kb.chunk_embeddings)]
  EV[POST /v1/admin/eval/runs] --> J2[(app.jobs)] --> WE[wf.eval.retrieval]
```

Compute stays outside n8n only where n8n cannot do it: tokenization and e5 embeddings (TEI), bge-m3 embeddings (Ollama), search and storage (PostgreSQL functions). Cleaning, structure parsing, chunking and metrics are plain JavaScript in `kb/` and `eval/lib/`, inlined into Code nodes by `n8n/build.py` and unit-tested with `node --test`.

### Match agent (D-084)

```mermaid
flowchart LR
  O[wf.orchestrator] -->|search_listings, or a follow-up within 30 min| A[wf.match.agent: AI Agent node]
  CM[Ollama Chat Model] -.model.- A
  MEM[(agent_memory.chat_histories)] -.memory.- A
  A -.tool.- TS[search_listings: wf.match.tool_search]
  A -.tool.- TL[listing_details: wf.match.tool_listing]
  TS --> P[wf.profile.extract P2] --> M[wf.match.search]
  TS --> SES[(ai.match_sessions)]
  TL --> SES
  A --> CHK[number check in code] --> R[answer + cards from the database]
  A -.fails.-> P
```

The agent decides when to search, rewrites follow-ups into a full request and writes a short answer. The search
itself is the fixed path (P2 with its checks, then `app.search_public`); the cards shown to the user come from the
database, not from the model's text, and an answer with a number that no tool gave is dropped.

### Legal agent (D-087)

```mermaid
flowchart LR
  O[wf.orchestrator] -->|legal_question, or a follow-up within 30 min| A[wf.legal.agent: AI Agent node]
  CM[Ollama Chat Model, 8192 ctx] -.model.- A
  MEM[(agent_memory.chat_histories, legal:user:id)] -.memory.- A
  A -.tool.- T[search_law: wf.legal.tool_search]
  T --> E[bge-m3 embedding] --> S[kb.search_chunks: country + global, top 5]
  S --> SES[(ai.legal_sessions: numbered excerpts)]
  A --> CHK[markers, abstention, numbers checked in code] --> R[answer + citations, or abstained]
  SES --> CHK
```

The model writes plain text with [n] after each claim, `[NOT_FOUND]` or `[CONFLICT]`; code keeps only markers of
excerpts that were retrieved, builds the citations (title, URL, type, reliability, article, retrieval date) from the
database, and abstains when nothing valid is cited or a number is in no excerpt. Telegram adds the notice.

### Owner assistant (D-088)

```mermaid
flowchart LR
  O[wf.orchestrator] -->|post_listing from a user with listings, or a follow-up| A[wf.owner.agent: AI Agent node]
  A -.tool.- L[my_listings] --> DB1[(app.listings: fields only)]
  A -.tool.- C[propose_change] --> CHK[app.listing_change_check] --> P[(ai.listing_changes: pending)]
  P --> T[Telegram: before -> after, Confirm / Cancel]
  P --> API[response: proposal]
  T -->|Confirm| PATCH[PATCH /v1/listings/:id change_id]
  API --> PATCH
  PATCH --> W[wf.listing.apply: check again, write, delete photos, embed]
```

Every LLM call except the agents' goes through `wf.llm.call`: the template and schema come from the registry, the model
from `llm.default_model` unless the caller names one. Agent steps (prompt version, model, tokens,
latency, errors; never the request text) are written to `ai.agent_steps` with the request record by
`app.api_finish`. Search, money conversion, geocoding and location fuzzing are PostgreSQL functions
(migration 0008); scoring of prompt outputs is `eval/lib/prompt_metrics.js`, inlined into the worker.

## Website and platform layer (platform P1, docs/PLATFORM_SPEC.md)

```mermaid
flowchart LR
  B[Browser] -->|https, port 3000| C[Caddy :3000]
  C -->|X-Forwarded-For| W[web: Next.js pages + server actions]
  W -->|sessions| ADB[(auth database)]
  W -->|signed /v1 call, X-Client-Ip| P[Caddy :8080]
  P --> G[wf.gateway.auth] --> E[wf.api.* platform workflow]
  E -->|select api.fn&#40;user, input&#41;| F[api functions, owner app_rls]
  F -->|RLS on app.current_user_id| T[(social, home, notify tables)]
  B -->|signed PUT, CORS for WEB_ORIGIN| P --> S[(Garage)]
  W -->|SMTP| M[Mailpit]
```

- Every page renders on the server. Forms post to server actions; each calls one API operation with an idempotency
  key generated when the page was shown. The browser never sees the API key and never calls n8n.
- Platform workflows (`n8n/build_platform.py`) all have the same nodes: webhook, route, gateway, shared validator
  with the endpoint's rules, one `api.*` call, result, envelope. The `api` functions set the caller first, so the
  forced RLS policies of the platform tables decide which rows exist for the caller (D-096). `n8n_worker` has no
  privilege on those tables.

| Workflow | Route | Function |
|---|---|---|
| `wf.api.me_get` | `GET /v1/me` | `api.me` |
| `wf.api.profiles_get` | `GET /v1/profiles/me` | `api.profile_get` |
| `wf.api.notifications_list` | `GET /v1/me/notifications` | `api.notifications_list` |
| `wf.api.notifications_read` | `POST /v1/me/notifications/read` | `api.notifications_read` |

Notifications are written by workflows with `api.notify_emit(user, type, params, link)`; the website writes the text
in the reader's language.


### Households (platform P5 and P6, D-104, D-105)

- Schema `home`, behind the row-level layer: households, members, invites, expenses and shares, settlements,
  recurring items, rent payments, announcements (P5); chores and assignments, shopping, house rules, events, issues
  (P6). Each operation is one `api.*` function, as in P4.
- Arithmetic in SQL: `api.split` (the three split modes), `api._balances` and `api.settle_plan` (suggested
  settlements); pure functions, tested on their own.
- `wf.household.daily` (05:00 UTC) calls `home.daily_reminders()`: rent and bill reminders in each household's date,
  once per due date; P6 adds the chore assignments.

## Flatmates and saved searches (platform P7)

- Tables `social.flatmate_profiles`, `social.saved_searches`, `social.saved_search_hits` (migration 0028), behind the
  row-level layer. A profile is visible to others only when its owner says so and nobody blocked anybody.
- `social.compatibility(a, b)` computes the score and the factor states from an allowlist of profile fields (D-106);
  the API returns it with each profile and, on the owner side, with applications to a household's room.
- `POST /v1/households/{id}/room-posts` -> `home.room_post`: a draft listing linked to the household, finished on the
  owner pages.
- `POST /v1/me/saved-searches` checks the query with the `/v2/search` code; `wf.household.daily` (05:00 UTC) runs
  reminders, then chores, then `social.daily_alerts()`, which sends each new matching listing once per search.
- Website: `/flatmates`, `/flatmates/[id]`, `/flatmates/me`, `/saved-searches`; "Save this search" on `/search`;
  "A room is free" on the household page.

## Trust and safety (platform P8)

- Submit: `wf.api.listings_submit` -> `app.listing_submit(user, id)` (P3 checks; 100 when the trust check is on) ->
  `wf.trust.assess` -> `app.listing_submit(user, id, {report_id})`: published, `pending_review` with a moderation item,
  or rejected (D-107).
- `wf.trust.assess`: `app.trust_facts` (database signals), the phrase lists of the packs (Code node), the Trust agent
  A4 (AI Agent node, `P4_trust_assessor`, tools in `wf.trust.tool`), `trust_rules.checkAgent` (quotes, payment
  confirmation), `app.trust_store` -> `app.trust_score` (caps, verdict) -> `app.trust_reports`.
